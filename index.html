The pattern

A planner and a repository executor, joined over stdio

Claude is the control plane: it clarifies the request, bounds the work, and judges the result. Codex is the execution plane: it inspects the real repository, makes the change, and runs the checks. Codex’s local MCP server carries a work order in and a result with a thread ID back out.

Core principle

Share a contract and observable artifacts—not hidden reasoning or assumed context.

Responsibility

Four owners, clean boundaries

Each participant owns a different kind of truth. That separation makes review concrete and escalation predictable.

01

Claude owns intent

Scope, priorities, acceptance criteria, work orders, evidence review, and concise delta feedback.

02

Codex owns execution

Repository inspection, implementation choices, edits, focused checks, diagnosis, and self-review.

03

The user owns decisions

Scope changes, destructive actions, new dependencies, external writes, and unresolved tradeoffs.

04

Artifacts own the facts

The working tree, git diff, tests, linters, and runtime checks outrank confident prose from either agent.

The write lease

One checkout. One writer. One coherent task.

While Codex holds the write lease, Claude stays read-only. It may inspect and review, but it does not “help” by editing the same files. If implementation really must run in parallel, each writer gets a separate worktree and explicit ownership.

What this rule removes

  • Colliding edits and generated-file churn
  • Reviews based on a stale working tree
  • Ambiguity about who introduced a change
  • Accidental loss of unrelated user work

End to end

The operating loop

Every transition produces something inspectable: a decision, a contract, a diff, test output, or a targeted correction.

  1. 1

    Clarify

    Resolve only ambiguities that materially change the result.

  2. 2

    Work order

    Define objective, scope, constraints, acceptance, and authority.

  3. 3

    Codex session

    Inspect → implement → test → self-review → report.

  4. 4

    Evidence review

    Map the actual diff and checks to every criterion.

  5. 5

    Delta feedback

    If a correctable gap remains, continue the same thread with exact evidence.

  6. 6

    Close

    Hand off when the agreed definition of done is proven—or surface the decision still needed.

Acceptableclose the task
Correctable gapsend delta feedback
Authority gapask the user

Connection

Register one local MCP server

The Claude host launches Codex as a local stdio server. Registration is user-scoped; no web service or shared secret sits between the agents.

shell claude mcp add --scope user codex -- codex mcp-server

The three-hour server timeout described below must also be configured. It is part of the working setup, not an optional performance tweak.

codexstart

Starts a bounded session with a prompt and overrides such as working directory, model, sandbox, approval policy, and reasoning configuration.

codex-replycontinue

Continues the same task with a saved threadId. Use it for evidence-backed review feedback rather than restating the whole contract.

Operational reality

Two facts that change the design

These are easy to miss in a happy-path demo and essential in a workflow meant to survive real tasks.

01Session lifetime

MCP threads live in memory

The MCP server keeps active threads in its in-memory ThreadManager. End the client session and the server process ends too. The rollout may still exist on disk, but codex-reply can no longer find that thread.

Design consequence

Finish delegate → review → revise inside one client session. Save every thread ID explicitly.

recovery codex exec resume <threadId> "<prompt>"

Use recovery to restore context and reconcile state, then open a fresh MCP thread with a concise work order before resuming implementation.

02Idle behavior

The three-hour timeout is load-bearing

The client aborts an idle stdio MCP call after 30 minutes. Codex emits codex/event notifications during a run, but those are not notifications/progress and do not reset the idle timer.

Default idle limit30 min
Configured per server3 hr
Design consequence

Set the server’s timeout to 10800000 milliseconds so a legitimate long-running, high-reasoning turn is not cut off without a useful result.

Compute policy

Start with Sol at high

Use gpt-5.6-sol with high reasoning for normal feature and bug-fix work. Escalate to xhigh when the change crosses subsystems, the root cause remains unclear, correctness depends on subtle invariants, or migration, security, or compatibility risk is high.

A useful distinction

Ultra≠xhigh

xhigh is reasoning effort for one run. Ultra is an orchestration mode that may divide independent work among subagents. Use it only when the work really splits safely—and never as a CLI synonym for xhigh.

Safety boundary

Fail safely; do not widen authority

The default lets Codex modify the selected workspace while preventing it from turning a blocked action into broader access.

Use workspace-write approval-policy: never

Codex can implement inside the authorized checkout. Anything outside that boundary must stop cleanly.

Never by convenience danger-full-access

Do not bypass the sandbox to keep momentum. A pause is cheaper than an unbounded side effect.

BLOCKED

Report the attempted action, why it is needed, the narrowest permission that would unblock it, and a safe alternative if one exists.

The takeaway

The contract is the interface. Evidence is the handoff.

Good orchestration is not more agent chatter. It is a clear outcome, narrow authority, one accountable writer, and a review loop that closes against observable facts.
